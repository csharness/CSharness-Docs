Environments let you maintain separate, isolated instances of your Google workspace configuration — each with its own data, API keys, and settings. Use environments to test integrations, try out new configurations, or validate content changes without touching your live production data. When you're confident your changes work as intended, you can promote them to production in a single step.

## What Environments Are

An environment in Google is a **fully isolated namespace** within your workspace. Each environment has:

- Its own **API keys** — a key issued in Staging cannot be used to access Production data, and vice versa.
- Its own **data store** — documents, pages, and resources created in one environment are not visible in another unless you explicitly promote them.
- Its own **settings snapshot** — integrations, webhooks, and configuration values can differ between environments.

Think of environments as parallel lanes for your workspace. Your team works safely in Staging or Development while end users and production systems interact only with Production.

## Default Environments

Every new Google workspace comes with two environments pre-configured:

| Environment | Purpose | Deletable |
|---|---|---|
| **Production** | Your live environment — serves real users and real data | No |
| **Staging** | A pre-production environment for testing changes | Yes |

You can rename the Staging environment or add additional environments to match your workflow (e.g., Development, QA, Preview).

<Info>
  The **Production** environment cannot be deleted or renamed. It is always the authoritative source for your live workspace data.
</Info>

## Creating a New Environment

You can create additional environments whenever your team needs a separate space — for a specific project, a client demo, or a QA review cycle.

<Steps>
  <Step title="Open Environments settings">
    Navigate to **Settings → Environments** in the left sidebar. You see a list of all existing environments with their names, creation dates, and current API key count.
  </Step>
  <Step title="Click New Environment">
    Click the **New Environment** button in the top-right corner of the Environments page.
  </Step>
  <Step title="Name your environment">
    Enter a descriptive name (e.g., `Development`, `QA`, `Client Preview`). The name appears in the environment switcher in the dashboard header.
  </Step>
  <Step title="Choose an initialization option">
    Select how to initialize the new environment:
    - **Empty** — start with no data or resources.
    - **Clone from existing** — copy the configuration and resources from another environment (data is copied at the time of creation; the two environments are independent after that).
  </Step>
  <Step title="Create the environment">
    Click **Create Environment**. Google provisions the new environment within a few seconds. You are automatically switched into it and can begin adding resources or generating API keys.
  </Step>
</Steps>

## Switching Environments in the Dashboard

The active environment is always shown in the **environment switcher** in the top navigation bar, next to your workspace name.

<Steps>
  <Step title="Locate the environment switcher">
    Look at the top navigation bar. You see your workspace name followed by the current environment name in a pill badge — for example, `My Workspace · Production`.
  </Step>
  <Step title="Open the switcher">
    Click the environment pill. A dropdown lists all available environments.
  </Step>
  <Step title="Select the target environment">
    Click the environment you want to switch to. The dashboard reloads and all data, resources, and API keys shown now belong to the selected environment.
  </Step>
</Steps>

<Warning>
  When you switch to **Production**, every action you take — creating, editing, or deleting resources — affects your live environment immediately. Always verify you are in the correct environment before making changes.
</Warning>

## Environment-Specific API Keys

API keys are scoped to a single environment. A key generated in Staging only works against Staging endpoints; it returns a `403 Forbidden` error if used against Production.

### Generating an environment-specific key

<Steps>
  <Step title="Switch to the target environment">
    Use the environment switcher to select the environment for which you want to generate a key.
  </Step>
  <Step title="Open API Keys settings">
    Navigate to **Settings → API Keys**. The keys listed here belong exclusively to the currently active environment.
  </Step>
  <Step title="Create the key">
    Click **New Key**, set the name, expiry, and scope, then click **Create Key**. Copy the key immediately — it is only shown once.
  </Step>
</Steps>

Use environment variables in your applications to store the correct key for each environment:

```bash title=".env.staging"
GOOGLE_API_KEY=sk_staging_xxxxxxxxxxxxxxxxxxxx
GOOGLE_ENV=staging
```

```bash title=".env.production"
GOOGLE_API_KEY=sk_production_xxxxxxxxxxxxxxxxxxxx
GOOGLE_ENV=production
```

```javascript title="Loading the correct key per environment"
// Node.js example — load the appropriate .env file at startup
import 'dotenv/config';

const client = new GoogleClient({
  apiKey: process.env.GOOGLE_API_KEY,
  environment: process.env.GOOGLE_ENV,
});
```

<Note>
  Never commit `.env` files to source control. Add them to your `.gitignore` and use a secrets manager or CI/CD environment variables to inject values at runtime.
</Note>

## Promoting Changes from Staging to Production

Once you have tested your changes in Staging and are ready to go live, you can promote the Staging environment to Production. Promotion copies resources, configuration, and content from Staging into Production.

<Warning>
  Promoting from Staging to Production **overwrites matching resources** in Production with the Staging versions. Resources that exist in Production but not in Staging are **not deleted** unless you select the **Replace all** option. Back up your Production data before promoting if you have any doubts — see [Data Management](/guides/data-management).
</Warning>

<Steps>
  <Step title="Review changes in Staging">
    Switch to the **Staging** environment and verify that all changes look correct. Check resources, settings, and integrations.
  </Step>
  <Step title="Open the Promote dialog">
    In **Settings → Environments**, find the Staging environment row and click the **⋯** menu. Select **Promote to Production**.
  </Step>
  <Step title="Choose what to promote">
    The Promote dialog shows a diff of what has changed since Staging was last synced with Production. Select the items you want to promote:
    - **Selected resources only** — promote specific pages or documents.
    - **All changes** — promote every change in Staging.
    - **Replace all** — promote all changes and remove Production resources that are not in Staging.
  </Step>
  <Step title="Confirm the promotion">
    Review the summary of changes, then click **Promote to Production**. Google applies the changes and shows a confirmation once the promotion is complete.
  </Step>
</Steps>

<Tip>
  Schedule promotions during low-traffic periods. While promotion is fast (typically under 30 seconds), brief inconsistencies in cached content are possible immediately after promotion completes.
</Tip>

For API-level details on environment-scoped requests, see [API Endpoints](/code/api/endpoints). For managing environment data exports and imports, see [Data Management](/guides/data-management).
