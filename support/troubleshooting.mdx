Most problems with Google fall into a small set of categories: authentication failures, permission mismatches, rate limiting, malformed import files, misconfigured webhooks, and performance bottlenecks. Work through the relevant section below to identify the root cause and apply a fix. If you're still stuck after following these steps, contact support from the **Help** menu in your dashboard.

<Tip>
  Many of the questions behind these issues are answered in the [FAQ](/support/faq) — check there first for quick answers about limits, key expiry, and team permissions.
</Tip>

## 401 Unauthorized

**Symptoms:** API requests return `401 Unauthorized`. The response body typically includes `"error": "invalid_token"` or `"error": "token_expired"`.

**Likely cause:** The API key is missing from the request, malformed, expired, or has been revoked.

<Steps>
  <Step title="Verify the key exists and is active">
    Open **Settings → API Keys** and confirm the key you're using has an **Active** status. If it shows **Expired** or **Revoked**, generate a replacement key and update your integration.
  </Step>
  <Step title="Check the Authorization header format">
    Google requires a Bearer token in the `Authorization` header. Confirm your request uses exactly this format — note the capital `B` and the single space:

    ```http title="Correct header format"
    Authorization: Bearer YOUR_API_KEY_HERE
    ```

    Common mistakes include using `Token` instead of `Bearer`, wrapping the key in quotes, or placing the key in a query parameter instead of the header.
  </Step>
  <Step title="Confirm you're targeting the right workspace">
    API keys are scoped to a single workspace. If you recently switched workspaces or are working in a new environment, make sure the key was generated inside the correct workspace. Keys from workspace A will always return `401` when used against workspace B's resources.
  </Step>
  <Step title="Check for whitespace or encoding issues">
    Copy-paste errors often introduce invisible whitespace around the key. If you're setting the key via an environment variable, print its exact length and compare it to the key displayed in the dashboard. Any mismatch indicates extra characters.

    ```bash title="Check key length"
    echo -n "$GOOGLE_API_KEY" | wc -c
    ```
  </Step>
</Steps>

<Note>
  If you're using the Google SDK, make sure you're initialising the client with the key and not a placeholder value like `"YOUR_API_KEY"`. See [SDK Installation](/code/sdk/installation) for the correct setup pattern.
</Note>

## 403 Forbidden

**Symptoms:** Requests return `403 Forbidden`. The response body usually contains `"error": "insufficient_scope"` or `"error": "permission_denied"`.

**Likely cause:** The API key exists and is valid, but it lacks the scopes required for the action you're attempting — or the team member making the request doesn't have the necessary role in the workspace.

<Steps>
  <Step title="Identify the required scope">
    Check the [API Endpoints reference](/code/api/endpoints) for the endpoint you're calling. Each endpoint lists the minimum required scope (for example, `write:documents` or `delete:keys`). Note the scope name.
  </Step>
  <Step title="Inspect your key's scopes">
    Go to **Settings → API Keys**, click **Edit** on the key in question, and review the **Permissions** checkboxes. Enable the scope identified in the previous step and save.
  </Step>
  <Step title="Check your team role">
    Some operations — such as managing billing or inviting team members — require the **Admin** role regardless of API key scopes. Ask a workspace Admin to grant you the appropriate role in **Settings → Team**.
  </Step>
</Steps>

<Warning>
  Avoid granting broad scopes (such as `*:*`) to API keys used in automated pipelines. Follow the principle of least privilege and grant only the scopes the integration actually needs. See [Security Best Practices](/code/advanced/security) for guidance.
</Warning>

## 429 Too Many Requests

**Symptoms:** After a burst of API calls, responses start returning `429 Too Many Requests`. Subsequent requests keep failing even when the payload is correct.

**Likely cause:** Your integration has exceeded the rate limit for your plan on the rolling 60-second window.

<Steps>
  <Step title="Read the Retry-After header">
    Every `429` response includes a `Retry-After` header containing the number of seconds you must wait before retrying:

    ```http title="429 response headers"
    HTTP/1.1 429 Too Many Requests
    Retry-After: 14
    X-RateLimit-Limit: 300
    X-RateLimit-Remaining: 0
    X-RateLimit-Reset: 1719859200
    ```

    Pause your request loop for at least that many seconds before continuing.
  </Step>
  <Step title="Implement exponential backoff">
    Instead of retrying immediately after the wait period, implement exponential backoff with jitter. Start with the `Retry-After` value, then double the delay on each subsequent `429`, adding a random jitter of ±10%:

    ```python title="Exponential backoff with jitter"
    import time, random

    def call_with_backoff(fn, max_retries=5):
        delay = 1
        for attempt in range(max_retries):
            response = fn()
            if response.status_code != 429:
                return response
            retry_after = int(response.headers.get("Retry-After", delay))
            sleep_time = retry_after * (2 ** attempt) + random.uniform(0, 0.1 * delay)
            time.sleep(sleep_time)
        raise Exception("Max retries exceeded")
    ```
  </Step>
  <Step title="Reduce request concurrency">
    Check whether your integration fires requests in parallel. Reduce the concurrency level or add a queue to throttle outbound requests to stay comfortably below your plan's requests-per-minute limit. Monitor `X-RateLimit-Remaining` proactively to slow down before hitting zero.
  </Step>
  <Step title="Consider a plan upgrade">
    If you regularly hit rate limits under normal operation, your workload may have outgrown your current plan. Review the limits table in [Rate Limits](/code/advanced/rate-limits) and upgrade in **Settings → Billing** if needed.
  </Step>
</Steps>

<Tip>
  The [FAQ](/support/faq#what-are-the-rate-limits-for-the-api) lists per-plan rate limit values if you need a quick reference.
</Tip>

## Import Fails

**Symptoms:** A CSV or JSON import job shows a **Failed** status. The import summary may display errors such as "Unexpected field", "Invalid encoding", or "Row parse error on line N".

**Likely cause:** The file contains formatting problems, uses an unsupported character encoding, or the column headers don't match the expected field names.

### CSV format issues

Confirm your CSV meets these requirements before retrying:

- **Encoding:** UTF-8 without BOM. Files saved as Windows-1252 or Latin-1 commonly fail.
- **Delimiter:** Comma (`,`). Tab-separated files must use the JSON import format instead.
- **Header row:** The first row must contain column names. Empty header cells are not permitted.
- **Quoting:** Fields containing commas or newlines must be wrapped in double quotes (`"`). Escape internal double quotes by doubling them (`""`).

<Steps>
  <Step title="Re-export with UTF-8 encoding">
    Open your spreadsheet in Excel or Google Sheets and use **File → Save As** or **File → Download** to export as CSV with UTF-8 encoding explicitly selected. On macOS, Numbers also defaults to UTF-8.
  </Step>
  <Step title="Validate field names against the template">
    Download the import template from **Data Management → Import → Download Template**. Compare your column headers exactly — casing matters. Rename any mismatched columns in your file.
  </Step>
  <Step title="Check for hidden characters">
    Run a quick check for non-printable characters or BOM markers:

    ```bash title="Detect BOM or non-UTF-8 characters"
    file -i your_import.csv
    head -c 3 your_import.csv | xxd
    ```

    If the `xxd` output starts with `ef bb bf`, a BOM is present. Strip it with:

    ```bash title="Strip BOM"
    sed -i '1s/^\xEF\xBB\xBF//' your_import.csv
    ```
  </Step>
  <Step title="Retry the import with row-level error logging">
    In the import dialog, enable **Skip invalid rows and log errors**. This lets valid rows through and produces a downloadable error report showing exactly which rows failed and why.
  </Step>
</Steps>

<Note>
  The maximum CSV file size is 50 MB (500,000 rows). For larger datasets, split the file or use the [bulk import API endpoint](/code/api/endpoints).
</Note>

## Webhook Not Firing

**Symptoms:** Events occur in Google (a document is updated, a key is created) but your webhook endpoint receives no HTTP request. The **Webhook Logs** panel shows no delivery attempts, or shows repeated failures.

**Likely cause:** The endpoint URL is unreachable, the event type is not subscribed, or the endpoint is rejecting the request before Google can confirm delivery.

<Steps>
  <Step title="Verify the endpoint URL is publicly reachable">
    Google cannot deliver webhooks to `localhost` or private network addresses. Use a tool like [ngrok](https://ngrok.com) during local development to expose your server, and deploy to a public URL for production. Confirm the URL returns a `2xx` status to a plain `POST` with an empty body.
  </Step>
  <Step title="Check your event subscriptions">
    Go to **Settings → Webhooks**, click the webhook, and review the **Events** list. If the checkbox for the event you expect (e.g. `document.updated`) is unchecked, enable it and save. Changes take effect immediately for new events.
  </Step>
  <Step title="Send a test delivery">
    Click **Send Test Event** on the webhook detail page. This fires a sample payload to your endpoint immediately. Check both the **Webhook Logs** panel for the delivery status and your server logs for the inbound request.
  </Step>
  <Step title="Confirm your endpoint returns 2xx quickly">
    Google marks a delivery as failed if your endpoint does not respond with a `2xx` status within **10 seconds**. If your handler performs heavy processing, return `200 OK` immediately and process the payload asynchronously. Any `4xx` or `5xx` response — including a redirect — is treated as a failure.
  </Step>
  <Step title="Review the delivery retry schedule">
    Failed deliveries are retried automatically on an exponential schedule: after 1 min, 5 min, 30 min, 2 hrs, and 8 hrs. Check the **Webhook Logs** panel to see whether retries are pending. If all retries are exhausted, you can manually re-trigger a delivery from the log entry.
  </Step>
</Steps>

<Tip>
  See [Webhooks](/code/api/webhooks) for the full payload schema and signature verification guide.
</Tip>

## Slow API Responses

**Symptoms:** API requests complete without errors but take several seconds to return. Dashboard pages load slowly. Search results are delayed.

**Likely cause:** A platform-wide incident, an inefficient query (large page size, no filters), or geographic latency between your client and the API servers.

<Steps>
  <Step title="Check the status page">
    Visit the Google status page (linked in the footer of your dashboard) to see whether a degraded-performance incident is currently active. If a degradation is reported, no action is needed on your side — subscribe to status updates to be notified when it resolves.
  </Step>
  <Step title="Reduce page size">
    Large `page_size` values force the API to fetch and serialise many records per request. Lower the value and paginate through results instead:

    ```http title="Use smaller page sizes"
    GET /v2/documents?page_size=25&cursor=eyJpZCI6IjEyMzQ1In0
    ```

    The default page size is 50; the maximum is 200. For most use cases, 25–50 is optimal.
  </Step>
  <Step title="Add filters to narrow result sets">
    Unfiltered list endpoints scan all records in your workspace. Apply filters to reduce the dataset:

    ```http title="Filter by status and date"
    GET /v2/documents?status=published&updated_after=2025-01-01T00:00:00Z
    ```

    See [API Endpoints](/code/api/endpoints) for the full list of supported filter parameters per resource.
  </Step>
  <Step title="Enable response compression">
    Add `Accept-Encoding: gzip` to your request headers to reduce payload size and transfer time. The Google API supports gzip compression on all JSON responses.

    ```http title="Request gzip compression"
    Accept-Encoding: gzip
    ```
  </Step>
</Steps>

<Note>
  If slow responses are limited to a specific endpoint or workspace, open a support ticket and include the `X-Request-Id` header value from the slow response. This allows the engineering team to trace the specific query.
</Note>
