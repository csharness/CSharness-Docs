Every request to the Google REST API must carry a valid credential. Google supports two authentication methods: **API Keys** for server-to-server integrations where you control the environment, and **OAuth 2.0** for applications acting on behalf of a user. Choose the method that fits your use case, then follow the steps below to start making authenticated requests.

## API Key Authentication

API keys are the fastest way to authenticate. They are long-lived tokens tied to your account (or a service account) and are best suited for backend scripts, CI pipelines, and server-side integrations where the key can be kept secret.

### Generate an API key

<Steps>
  <Step title="Open the Dashboard">
    Navigate to your workspace and select **Settings → API Keys** from the left sidebar.
  </Step>
  <Step title="Create a new key">
    Click **New API Key**, enter a descriptive name (for example, `ci-pipeline-key`), and choose an expiry — or select **No expiry** for a permanent key.
  </Step>
  <Step title="Copy the key">
    The key is shown only once. Copy it immediately and store it in a secrets manager or environment variable. Google never displays the raw key again.
  </Step>
</Steps>

<Warning>
  Never commit API keys to source control. Use environment variables or a secrets manager such as HashiCorp Vault, AWS Secrets Manager, or GitHub Actions secrets.
</Warning>

### Pass the API key in a request

Include the key in the `Authorization` header using the `Bearer` scheme:

```bash title="Authenticated request with an API key"
curl -X GET https://api.google.example/v1/resources \
  -H "Authorization: Bearer YOUR_API_KEY"
```

<Note>
  All requests must use HTTPS. HTTP requests are rejected with `400 Bad Request` regardless of the credentials supplied.
</Note>

## OAuth 2.0 Authentication

OAuth 2.0 lets your application request access on behalf of a Google user. Google implements the **Authorization Code** flow, which is suitable for web and server-side applications.

### Scopes

Request only the scopes your application needs. Requesting unnecessary scopes will cause users to reject the authorization prompt.

| Scope | Access granted |
|---|---|
| `read` | Read all resources, projects, and workspace data |
| `write` | Create and update resources and projects |
| `admin` | Manage workspace settings, members, and billing |
| `webhooks` | Register, list, and delete webhook endpoints |

### Step 1 — Redirect the user

Send the user to Google's authorization endpoint. Build the redirect URL with the following query parameters:

<ParamField query="client_id" type="string" required>
  Your application's OAuth client ID, obtained from **Settings → OAuth Apps**.
</ParamField>

<ParamField query="redirect_uri" type="string" required>
  The URI Google redirects to after the user approves or denies access. Must exactly match a URI registered in your OAuth app settings.
</ParamField>

<ParamField query="response_type" type="string" required>
  Must be `code` for the Authorization Code flow.
</ParamField>

<ParamField query="scope" type="string" required>
  Space-separated list of requested scopes, for example `read write`.
</ParamField>

<ParamField query="state" type="string">
  An opaque, randomly generated value you use to prevent CSRF attacks. Verify that the same value is returned in the callback.
</ParamField>

```bash title="Authorization redirect URL (example)"
https://auth.google.example/oauth/authorize
  ?client_id=YOUR_CLIENT_ID
  &redirect_uri=https://yourapp.example/callback
  &response_type=code
  &scope=read%20write
  &state=abc123xyz
```

### Step 2 — Exchange the code for tokens

After the user approves, Google redirects to your `redirect_uri` with a short-lived `code` query parameter. Exchange this code for an access token and a refresh token:

<ParamField body="grant_type" type="string" required>
  Must be `authorization_code`.
</ParamField>

<ParamField body="code" type="string" required>
  The authorization code received in the redirect callback.
</ParamField>

<ParamField body="redirect_uri" type="string" required>
  Must exactly match the `redirect_uri` used in Step 1.
</ParamField>

<ParamField body="client_id" type="string" required>
  Your application's client ID.
</ParamField>

<ParamField body="client_secret" type="string" required>
  Your application's client secret, obtained from **Settings → OAuth Apps**.
</ParamField>

```bash title="Token exchange request"
curl -X POST https://auth.google.example/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code" \
  -d "code=AUTH_CODE_FROM_CALLBACK" \
  -d "redirect_uri=https://yourapp.example/callback" \
  -d "client_id=YOUR_CLIENT_ID" \
  -d "client_secret=YOUR_CLIENT_SECRET"
```

A successful response returns:

```json title="Token exchange response"
{
  "access_token": "eyJhbGciOiJSUzI1NiJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "def50200abc...",
  "scope": "read write"
}
```

### Step 3 — Use the access token

Pass the access token in the `Authorization` header exactly as you would an API key:

```bash title="Authenticated request with an OAuth access token"
curl -X GET https://api.google.example/v1/resources \
  -H "Authorization: Bearer ACCESS_TOKEN"
```

### Step 4 — Refresh the access token

Access tokens expire after one hour (`expires_in: 3600`). Use the refresh token to obtain a new access token without re-prompting the user:

<ParamField body="grant_type" type="string" required>
  Must be `refresh_token`.
</ParamField>

<ParamField body="refresh_token" type="string" required>
  The refresh token returned in the original token exchange.
</ParamField>

<ParamField body="client_id" type="string" required>
  Your application's client ID.
</ParamField>

<ParamField body="client_secret" type="string" required>
  Your application's client secret.
</ParamField>

```bash title="Token refresh request"
curl -X POST https://auth.google.example/oauth/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=refresh_token" \
  -d "refresh_token=YOUR_REFRESH_TOKEN" \
  -d "client_id=YOUR_CLIENT_ID" \
  -d "client_secret=YOUR_CLIENT_SECRET"
```

<Tip>
  Proactively refresh the access token a minute or two before it expires rather than waiting for a `401 token_expired` error. Store the `expires_in` timestamp alongside the token.
</Tip>

## Authentication Errors

| HTTP Status | Error Code | Meaning |
|---|---|---|
| `401` | `unauthorized` | No credential was provided, or the credential is malformed. |
| `401` | `token_expired` | The OAuth access token has expired. Refresh it and retry. |
| `403` | `forbidden` | The credential is valid but the account lacks permission for this resource. |
| `403` | `insufficient_scope` | The OAuth token does not include the required scope. Re-authorize with broader scopes. |

See the [Errors reference](/code/api/errors) for the full list of error codes and handling guidance.
