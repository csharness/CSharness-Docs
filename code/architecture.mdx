Before writing your first integration, it helps to understand how the Google API is shaped. The API follows RESTful conventions throughout: resources are nouns, HTTP verbs express intent, and every response comes back in a predictable envelope. This page explains the mental model you need to work efficiently with any endpoint in the API.

## Resource Model

Resources in Google are organized in a three-level hierarchy:

```
Workspace
  └── Project
        └── Resource (document, knowledge base, snippet, …)
```

- **Workspaces** are the top-level organizational unit. Your account can belong to one or more workspaces.
- **Projects** live inside workspaces and group related content together.
- **Resources** (documents, knowledge bases, snippets, etc.) live inside projects.

This hierarchy is reflected directly in URL paths. A request to a specific document looks like:

```
GET /v1/workspaces/{workspace_id}/projects/{project_id}/documents/{document_id}
```

You always address a child resource through its parent chain, which means every resource ID is globally unique within its type but API paths make ownership explicit.

## RESTful Conventions

Google's API uses standard HTTP semantics. Use the verb that matches your intent:

| HTTP Verb | Meaning |
|---|---|
| `GET` | Retrieve a resource or list of resources |
| `POST` | Create a new resource |
| `PATCH` | Partially update an existing resource |
| `PUT` | Replace an existing resource entirely |
| `DELETE` | Remove a resource |

Request bodies for `POST`, `PATCH`, and `PUT` must be JSON with the `Content-Type: application/json` header set. `GET` and `DELETE` requests do not include a body.

## Standard Response Envelope

Every response — success or error — is wrapped in a consistent envelope with three top-level keys:

```json
{
  "data": { ... },
  "meta": { ... },
  "errors": []
}
```

| Key | Description |
|---|---|
| `data` | The primary payload — a single object for item endpoints, an array for list endpoints |
| `meta` | Metadata about the response: pagination cursors, total counts, request IDs |
| `errors` | An array of error objects; empty on success, populated on 4xx/5xx responses |

<Note>
  Even when a request fails, the response body always conforms to this envelope shape. Parse `errors` to understand what went wrong. The `data` key will be `null` on error responses.
</Note>

## Pagination

List endpoints return results in pages using **cursor-based pagination**. Offset-based pagination (`page=2`) is not supported because it can miss or duplicate records when the underlying data changes between requests.

Each list response includes pagination information inside the `meta` object:

```json
{
  "data": [
    { "id": "doc_01HXZ9KQMB3V", "title": "Getting Started Guide" },
    { "id": "doc_01HXZ9KQMB4W", "title": "API Reference" }
  ],
  "meta": {
    "cursor": {
      "next_cursor": "cur_eyJpZCI6ImRvY18wMUhYWjlLUU1CNFcifQ",
      "has_more": true
    },
    "request_id": "req_01HXZ9KQMBFG"
  },
  "errors": []
}
```

To fetch the next page, pass the `next_cursor` value as the `cursor` query parameter in your next request:

```bash
GET /v1/workspaces/{workspace_id}/projects/{project_id}/documents?cursor=cur_eyJpZCI6ImRvY18wMUhYWjlLUU1CNFcifQ
```

When `has_more` is `false`, you have reached the last page. A missing or `null` `next_cursor` also signals the end of results.

<Tip>
  Use a `limit` query parameter (default `20`, maximum `100`) to control how many items are returned per page and tune the trade-off between request count and payload size.
</Tip>

## Filtering

Filter list results by appending `filter[field]=value` query parameters. Multiple filters are combined with a logical AND:

```bash
GET /v1/workspaces/{workspace_id}/projects?filter[status]=active&filter[visibility]=public
```

String filters perform exact matches by default. Prefix the value with operators for richer queries:

| Syntax | Example | Meaning |
|---|---|---|
| `value` | `filter[status]=active` | Exact match |
| `prefix:value` | `filter[title]=prefix:API` | Starts with |
| `contains:value` | `filter[title]=contains:guide` | Contains substring |
| `gt:value` | `filter[created_at]=gt:2025-01-01T00:00:00Z` | Greater than |
| `lt:value` | `filter[created_at]=lt:2025-06-01T00:00:00Z` | Less than |

<Info>
  Not every field supports every operator. The individual endpoint reference pages list the filterable fields and which operators they accept.
</Info>

## Sorting

Control the order of list results with the `sort` query parameter. Prefix the field name with `-` to sort in descending order:

```bash
# Ascending — oldest first
GET /v1/.../documents?sort=created_at

# Descending — newest first
GET /v1/.../documents?sort=-created_at
```

Some endpoints support multi-field sorting by passing a comma-separated list:

```bash
GET /v1/.../documents?sort=-updated_at,title
```

## Field Selection

Reduce payload size by requesting only the fields you need using the `fields` query parameter:

```bash
GET /v1/.../documents?fields=id,title,created_at
```

The response `data` objects will include only the specified fields. This is particularly useful in list responses where you only need identifiers and display names.

<Warning>
  Always include `id` in your field selection if you plan to use the response objects to make subsequent requests. Omitting it can cause hard-to-debug errors downstream.
</Warning>
