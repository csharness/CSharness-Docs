Google enforces rate limits on all API requests to ensure fair usage and platform stability for every user. Understanding how these limits work — and building your integration to respect them — prevents unexpected 429 errors from disrupting your application in production. This page explains the limits for each plan, how to read the headers Google returns on every response, and the techniques you can apply to stay well within your quota.

## Rate Limits by Plan

Your rate limit tier is determined by the plan your account is on. If you need higher throughput than your current plan allows, you can upgrade in the [billing settings](/configuration/settings) or contact sales for an Enterprise quote.

| Plan       | Requests per Minute | Requests per Day | Burst Allowance |
|------------|---------------------|------------------|-----------------|
| Free       | 100                 | 10,000           | Up to 120 for 5 s |
| Pro        | 1,000               | 500,000          | Up to 1,200 for 5 s |
| Enterprise | Custom              | Custom           | Negotiated      |

<Note>
  Burst allowance lets your application briefly exceed the per-minute limit during a short spike. Sustained traffic above the limit still results in a `429` response.
</Note>

## Rate Limit Response Headers

Google includes rate limit metadata in the headers of **every** API response, not just errors. Read these headers in your client to track consumption in real time and act before you hit the ceiling.

```http title="Sample API Response Headers"
HTTP/1.1 200 OK
Content-Type: application/json
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 847
X-RateLimit-Reset: 1714512000
Retry-After: 0
```

| Header | Type | Description |
|---|---|---|
| `X-RateLimit-Limit` | integer | Total requests allowed in the current window |
| `X-RateLimit-Remaining` | integer | Requests remaining before the limit resets |
| `X-RateLimit-Reset` | Unix timestamp | The UTC epoch second at which the window resets |
| `Retry-After` | integer (seconds) | How long to wait before retrying; `0` when not rate-limited |

## When You Hit the Limit (429)

When your application exceeds its rate limit, Google returns an HTTP `429 Too Many Requests` response. The response body describes the error and the `Retry-After` header tells you exactly how many seconds to wait.

```json title="429 Response Body"
{
  "error": {
    "code": 429,
    "type": "rate_limit_exceeded",
    "message": "You have exceeded your request rate limit. Please retry after the indicated delay.",
    "retry_after": 14
  }
}
```

<Warning>
  Do not immediately retry on a `429` without waiting. A tight retry loop will continue to hit the limit, extend your back-off window, and potentially trigger a temporary IP-level block on Enterprise plans.
</Warning>

## Strategies for Staying Within Your Limits

Adopt one or more of the following patterns to build a resilient integration that degrades gracefully under load.

<Tabs>
  <Tab title="Exponential Backoff">
    Exponential backoff waits progressively longer between retries, giving the rate limit window time to reset without hammering the API.

    ```javascript title="exponentialBackoff.js"
    async function fetchWithBackoff(url, options = {}, maxRetries = 5) {
      let attempt = 0;

      while (attempt < maxRetries) {
        const response = await fetch(url, options);

        if (response.status !== 429) {
          return response;
        }

        const retryAfter = parseInt(response.headers.get("Retry-After") || "1", 10);
        const jitter = Math.random() * 1000; // up to 1 s of random jitter
        const delay = Math.max(retryAfter * 1000, Math.pow(2, attempt) * 1000) + jitter;

        console.warn(`Rate limited. Retrying in ${(delay / 1000).toFixed(1)} s (attempt ${attempt + 1}/${maxRetries})`);
        await new Promise((resolve) => setTimeout(resolve, delay));
        attempt++;
      }

      throw new Error(`Request failed after ${maxRetries} retries due to rate limiting.`);
    }

    // Usage
    const response = await fetchWithBackoff("https://api.google.com/v1/documents", {
      headers: { Authorization: `Bearer ${process.env.GOOGLE_API_KEY}` },
    });
    const data = await response.json();
    ```

    <Tip>
      Always add random **jitter** to your backoff delay. Without it, multiple parallel clients that hit the limit simultaneously will retry at the exact same moment and collide again.
    </Tip>
  </Tab>

  <Tab title="Request Queuing">
    A client-side queue serialises outbound requests, releasing them at a controlled rate that stays under your plan limit.

    ```javascript title="requestQueue.js"
    class RateLimitedQueue {
      constructor(requestsPerMinute) {
        this.interval = (60 * 1000) / requestsPerMinute; // ms between requests
        this.queue = [];
        this.running = false;
      }

      enqueue(fn) {
        return new Promise((resolve, reject) => {
          this.queue.push({ fn, resolve, reject });
          if (!this.running) this._run();
        });
      }

      async _run() {
        this.running = true;
        while (this.queue.length > 0) {
          const { fn, resolve, reject } = this.queue.shift();
          try {
            resolve(await fn());
          } catch (err) {
            reject(err);
          }
          await new Promise((r) => setTimeout(r, this.interval));
        }
        this.running = false;
      }
    }

    // Throttle to 900 req/min to leave a 10 % safety margin on a Pro plan
    const queue = new RateLimitedQueue(900);

    const result = await queue.enqueue(() =>
      fetch("https://api.google.com/v1/documents", {
        headers: { Authorization: `Bearer ${process.env.GOOGLE_API_KEY}` },
      }).then((r) => r.json())
    );
    ```
  </Tab>

  <Tab title="Request Batching">
    Many Google API endpoints accept batched payloads, letting you process multiple records in a single HTTP round-trip and dramatically reduce your per-minute count.

    ```javascript title="batchRequest.js"
    // Instead of one request per document ID…
    const documentIds = ["doc_1", "doc_2", "doc_3", "doc_4", "doc_5"];

    const response = await fetch("https://api.google.com/v1/documents/batch", {
      method: "POST",
      headers: {
        Authorization: `Bearer ${process.env.GOOGLE_API_KEY}`,
        "Content-Type": "application/json",
      },
      body: JSON.stringify({ ids: documentIds }),
    });

    const { documents } = await response.json();
    ```

    <Note>
      The batch endpoint counts as **one request** against your rate limit regardless of how many items are in the payload. The maximum batch size is 100 items per request.
    </Note>
  </Tab>
</Tabs>

## Monitoring Your Usage

Beyond the response headers, you can track your API consumption in the **Usage** tab of the Google dashboard. The graph updates every five minutes and shows request volume broken down by endpoint, response status, and time of day — making it straightforward to identify the hotspots in your integration before they become a problem.
