Securing your Google integration is not a one-time task — it is a continuous practice that spans how you store credentials, how you receive webhook events, and how you manage the entire lifecycle of access tokens. The guidance on this page covers the most common attack surfaces and the concrete steps you can take to close them. Apply these practices from day one; retrofitting security into an existing integration is significantly harder than building it in correctly from the start.

## Protecting API Keys

Your API key grants full programmatic access to your Google account. Treat it with the same care as a password.

<Warning>
  **Never embed an API key directly in client-side code, mobile app bundles, or public repositories.** Once a key is committed to a public repo or shipped in a front-end bundle, you must consider it compromised and rotate it immediately. Secret-scanning bots index GitHub continuously.
</Warning>

### Store Credentials in Environment Variables

Keep secrets out of your source code entirely by loading them from environment variables at runtime.

```bash title=".env"
# Google API credentials — never commit this file
GOOGLE_API_KEY=goog_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
GOOGLE_WEBHOOK_SECRET=whsec_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
GOOGLE_OAUTH_CLIENT_SECRET=ocs_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

```javascript title="client.js"
// Load environment variables before any other imports
import "dotenv/config";

const apiKey = process.env.GOOGLE_API_KEY;

if (!apiKey) {
  throw new Error("GOOGLE_API_KEY is not set. Check your .env file or deployment environment.");
}
```

<Tip>
  Enable **secret scanning** in your repository host (GitHub, GitLab, Bitbucket all offer this natively). Google is a registered token partner, so commits containing a valid Google API key will trigger an automatic alert — and Google will immediately revoke the exposed key to protect your account.
</Tip>

Make sure your `.gitignore` always excludes environment files:

```bash title=".gitignore"
# Environment files — never commit
.env
.env.local
.env.*.local
```

## Scoping API Keys

When you create an API key in the Google dashboard, restrict it to only the scopes your application actually uses. A key scoped to `documents:read` cannot be used to delete data even if it is stolen.

<Tabs>
  <Tab title="Recommended Scopes">

    | Use Case | Minimum Required Scopes |
    |---|---|
    | Read-only dashboard | `documents:read`, `spaces:read` |
    | Content publishing | `documents:read`, `documents:write` |
    | Full admin automation | `documents:*`, `spaces:*`, `members:read` |
    | Webhook registration | `webhooks:write` |

  </Tab>
  <Tab title="Creating a Scoped Key">

    <Steps>
      <Step title="Open API Keys">
        Navigate to **Settings → API Keys** in the Google dashboard and click **Create New Key**.
      </Step>
      <Step title="Select Scopes">
        Under **Permissions**, deselect all scopes and then enable only the ones your application requires. Avoid selecting wildcard (`*`) scopes unless your use case demands them.
      </Step>
      <Step title="Set an Expiry">
        Choose an expiry date appropriate for your use case. Short-lived keys (30–90 days) reduce the blast radius of a leak.
      </Step>
      <Step title="Save and Copy Once">
        Copy the key immediately after creation — Google displays it only once. Store it in your secrets manager or `.env` file right away.
      </Step>
    </Steps>

  </Tab>
</Tabs>

## Rotating API Keys

Rotate your API keys on a regular schedule and **immediately** whenever you suspect a key has been exposed.

<Steps>
  <Step title="Generate a Replacement Key">
    In **Settings → API Keys**, create a new key with the same scopes as the one you are replacing.
  </Step>
  <Step title="Deploy the New Key">
    Update your environment variables or secrets manager with the new key value and redeploy your application.
  </Step>
  <Step title="Verify Traffic">
    Monitor your API usage graph for a few minutes to confirm requests are succeeding with the new key.
  </Step>
  <Step title="Revoke the Old Key">
    Return to **Settings → API Keys**, select the old key, and click **Revoke**. Traffic using the old key will immediately begin returning `401` errors.
  </Step>
</Steps>

<Note>
  Google's dashboard shows the **last used** timestamp for every key. Use this to identify stale or unused keys and revoke them proactively — unused keys are unnecessary attack surface.
</Note>

## Verifying Webhook Signatures

Every webhook request Google sends to your endpoint includes an `X-Google-Signature` header. This is an HMAC-SHA256 signature computed from the raw request body and your webhook secret. **Always verify this signature before processing the payload** — without verification, an attacker can forge requests to your endpoint.

<Warning>
  Do not compute the signature from a parsed JSON object. Parse the raw request bytes first, verify the signature, and only then deserialize the body. Whitespace differences between serializers will cause valid signatures to fail.
</Warning>

```javascript title="webhookHandler.js"
import crypto from "crypto";

export function verifyWebhookSignature(rawBody, signatureHeader, secret) {
  const expectedSignature = crypto
    .createHmac("sha256", secret)
    .update(rawBody) // rawBody must be a Buffer or raw string, not parsed JSON
    .digest("hex");

  const trusted = Buffer.from(`sha256=${expectedSignature}`, "utf8");
  const received = Buffer.from(signatureHeader, "utf8");

  // Use timingSafeEqual to prevent timing attacks
  if (trusted.length !== received.length) return false;
  return crypto.timingSafeEqual(trusted, received);
}

// Express example — ensure bodyParser is NOT applied before this route
app.post("/webhooks/google", express.raw({ type: "application/json" }), (req, res) => {
  const signature = req.headers["x-google-signature"];

  if (!verifyWebhookSignature(req.body, signature, process.env.GOOGLE_WEBHOOK_SECRET)) {
    return res.status(401).json({ error: "Invalid webhook signature" });
  }

  const event = JSON.parse(req.body.toString("utf8"));
  // Safe to process the verified event
  console.log("Received event:", event.type);
  res.status(200).json({ received: true });
});
```

<Tip>
  Use `crypto.timingSafeEqual` (Node.js) or an equivalent constant-time comparison in your language. Standard string equality (`===`) is vulnerable to timing attacks that can be used to forge signatures.
</Tip>

### Webhook Endpoint Requirements

<CardGroup cols={2}>
  <Card title="HTTPS Only" icon="lock">
    Google will not deliver events to plain HTTP endpoints. Your webhook URL must use TLS with a valid, publicly trusted certificate.
  </Card>
  <Card title="Respond Quickly" icon="bolt">
    Return a `200` response within 5 seconds. Offload heavy processing to a background queue so you acknowledge the event immediately.
  </Card>
  <Card title="Idempotency" icon="arrows-rotate">
    Google may retry delivery on network failures. Use the `event.id` field as an idempotency key so duplicate deliveries do not cause duplicate side effects.
  </Card>
  <Card title="Allowlist Google IPs" icon="shield">
    For extra defence, restrict your webhook route to [Google's published IP ranges](/support/faq) using firewall rules or middleware.
  </Card>
</CardGroup>

## OAuth Token Handling

If your integration uses OAuth rather than static API keys, apply these additional safeguards.

<Accordion title="Store tokens in a server-side secrets store">
  Never store OAuth access tokens or refresh tokens in browser `localStorage`, `sessionStorage`, or client-readable cookies. These are accessible to any JavaScript running on the page, including third-party scripts. Store them server-side in an encrypted database column or a dedicated secrets manager (AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager).
</Accordion>

<Accordion title="Use short-lived access tokens with refresh">
  Google access tokens expire after one hour by default. Do not extend token expiry for convenience — instead, implement the refresh token flow to obtain a fresh access token automatically. This limits the window during which a stolen token is usable.

  ```javascript title="tokenRefresh.js"
  async function getValidAccessToken(storedTokens) {
    const expiresAt = new Date(storedTokens.expires_at);
    const now = new Date();
    const bufferMs = 5 * 60 * 1000; // refresh 5 minutes before expiry

    if (expiresAt - now > bufferMs) {
      return storedTokens.access_token; // still valid
    }

    const response = await fetch("https://api.google.com/oauth/token", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        grant_type: "refresh_token",
        refresh_token: storedTokens.refresh_token,
        client_id: process.env.GOOGLE_OAUTH_CLIENT_ID,
        client_secret: process.env.GOOGLE_OAUTH_CLIENT_SECRET,
      }),
    });

    const newTokens = await response.json();
    await saveTokensToDatabase(newTokens); // persist the refreshed tokens
    return newTokens.access_token;
  }
  ```
</Accordion>

<Accordion title="Revoke tokens on user sign-out">
  Call the Google token revocation endpoint whenever a user logs out of your application. Relying solely on token expiry leaves a valid token floating in memory or logs longer than necessary.
</Accordion>

## Auditing Key Usage

The **Settings → API Keys → Usage Logs** view in the Google dashboard shows a full history of which keys made requests, to which endpoints, and when. Review this log periodically to:

- Detect unexpected spikes that may indicate key misuse.
- Identify unused keys that can be safely revoked.
- Confirm that scoped keys are only accessing the endpoints they should.

<Note>
  Enterprise plans have access to exportable audit logs in JSON format, which you can ingest into your SIEM for automated alerting on anomalous patterns.
</Note>

## Security Checklist

<Accordion title="Run through this checklist before going to production">

  - [ ] API keys are stored in environment variables, not in source code.
  - [ ] `.env` files are listed in `.gitignore`.
  - [ ] Secret scanning is enabled on your repository.
  - [ ] Each API key is scoped to the minimum required permissions.
  - [ ] Keys have an expiry date set.
  - [ ] Webhook signature verification is implemented using `timingSafeEqual`.
  - [ ] Webhook endpoint uses HTTPS with a valid certificate.
  - [ ] Webhook handler responds within 5 seconds and queues heavy work.
  - [ ] OAuth tokens are stored server-side only.
  - [ ] Token refresh logic runs before the access token expires.
  - [ ] A key rotation runbook exists and has been tested.

</Accordion>
